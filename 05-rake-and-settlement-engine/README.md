# 05 — Rake Engine and Monetary Settlement Flow

**Chain Poker Genesis by LAEV (peroqtdigo)**
**Engine:** Rake Engine / Monetary Settlement Flow
**Version:** 1.0 reconstruction
**Historical source:** 5.0_Rake Engine and Monetary Settlement Flow_CPG.pdf

## Boundary

Engine 05 owns rake eligibility evaluation, deterministic rake calculation, allocation calculation, creation of the canonical rake obligation, ledger evidence for that obligation, and settlement request creation.

It does not own poker hand evaluation, card generation, player permissions, private card disclosure, Bitcoin private-key custody, or final transaction execution.

## Default configuration

For the reconstructed v1.0 configuration:

rake = eligible_pot × 0.03
foundation = rake × 0.11
akamoto = rake × 0.89

The two allocations must equal the complete rake amount.

## Canonical lifecycle

HAND_COMPLETED → RAKE_ELIGIBILITY_EVALUATED → RAKE_CALCULATED → RAKE_RECORDED → SETTLEMENT_REQUESTED → Monetary Settlement Engine → SETTLEMENT_CONFIRMED

The exact global state machine remains dependent on Poker Rules, Table Wallet, Permissions and Settlement specifications.

## Canonical obligation

Conceptual object:

RakeObligation {
  protocol_version
  table_id
  hand_id
  rake_event_id
  eligible_pot
  rake_amount
  foundation_amount
  external_destination_amount
  source_wallet_context
  status
}

The final schema remains to be formalized.

## Idempotency

One completed hand must not generate duplicate canonical rake obligations. Settlement retries must not create additional monetary obligations.

The obligation identifier is the bridge between hand completion, ledger evidence, settlement request, settlement transaction and reconciliation.

## Engine 04 interaction

Engine 04 records evidence generated by Engine 05. Recommended events are RAKE_ELIGIBILITY_EVALUATED, RAKE_CALCULATED, RAKE_OBLIGATION_CREATED, SETTLEMENT_REQUESTED, SETTLEMENT_CONFIRMED and SETTLEMENT_FAILED.

Engine 04 records evidence; it does not calculate the rake.

## Engine 06 interaction

Engine 06 is cryptographic card privacy infrastructure and has no direct authority over rake. The dependency is indirect: card/hand lifecycle → Poker Rules → HAND_COMPLETED → Engine 05.

Engine 05 must never infer hand completion from card-reveal UI or a player's assertion. It consumes an authorized protocol state transition.

## Wallet and permissions boundary

The Table Wallet Engine provides operational monetary context. Engine 05 determines the obligation. The Monetary Settlement Engine performs the transfer. Private keys remain outside Engine 05 and the ledger.

The Requests and Permissions Engine controls authorization. Engine 05 may create a settlement request but should not become its own authorization authority.

## Determinism

For identical canonical inputs, Engine 05 must produce identical rake amount, allocation amounts, obligation identity inputs and state-transition result.

Production determinism additionally requires unresolved precision rules to be formally defined.

## Specification gaps

Before production implementation, the protocol must define complete rake eligibility, side-pot treatment, split-pot treatment, uncalled bets, aborted/disconnected hands, satoshi-level rounding, dust handling, Bitcoin network-fee treatment, settlement batching, confirmation requirements, reorg handling, failed settlement recovery, destination rotation and reconciliation rules.

These are intentionally not invented here.

## Security invariants

1. Rake cannot exceed the eligible pot.
2. Allocation totals equal the rake.
3. One hand cannot create duplicate canonical obligations.
4. Settlement retries are idempotent.
5. Private keys never enter Engine 05 records.
6. Every monetary transition has a corresponding ledger event.
7. Failed transfers remain distinguishable from completed transfers.
