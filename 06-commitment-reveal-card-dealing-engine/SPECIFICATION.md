# Engine 06 — Functional Cryptographic Specification

## 1. Scope

This specification defines the functional contract for private card commitments and authorized reveals.

It does not define poker hand ranking or settlement.

## 2. State machine

`UNINITIALIZED → COMMITTED → PRIVATE → REVEAL_REQUESTED → REVEALED`

Terminal rejection paths:

`COMMITTED → INVALID`  
`REVEAL_REQUESTED → REJECTED`

The exact global hand-state transition rules remain under the Poker Rules Engine and Requests and Permissions Engine.

## 3. Commitment object

Conceptual structure:

```text
Commitment {
  protocol_id
  protocol_version
  table_id
  hand_id
  player_id
  commitment_id
  commitment_hash
  signature
}
```

The commitment hash commits to the private card material plus a cryptographically secure nonce and the protocol domain.

## 4. Protected card object

Conceptual structure:

```text
ProtectedCards {
  commitment_id
  encryption_version
  ciphertext
  nonce_or_iv
  authentication_tag
}
```

The encryption object is intentionally separate from the commitment object.

## 5. Reveal object

Conceptual structure:

```text
Reveal {
  protocol_id
  protocol_version
  table_id
  hand_id
  player_id
  commitment_id
  canonical_card_data
  commitment_nonce
  authorization_signature
}
```

## 6. Verification equation

The verifier calculates:

`H(protocol_domain || hand_id || player_id || canonical_card_data || commitment_nonce)`

and compares the result against the stored commitment hash.

A valid equality establishes cryptographic consistency with the committed data, subject to the security assumptions of the selected hash and canonicalization scheme.

## 7. Privacy rule

The public protocol state must never require publication of private card plaintext before the rules authorize a reveal.

## 8. Authorization rule

A valid commitment does not automatically authorize a reveal.

Reveal acceptance requires both:

- protocol-state authorization; and
- any player/wallet authorization required by the protocol.

## 9. Determinism and randomness

Commitment generation must be deterministic from its defined inputs.

Card assignment randomness must be generated by the protocol's designated randomness mechanism. It must not be derived from a predictable commitment value.

## 10. Audit events

The following events are recommended:

- CARD_COMMITMENT_CREATED
- CARD_REVEAL_REQUESTED
- CARD_REVEAL_AUTHORIZED
- CARD_REVEAL_ACCEPTED
- CARD_REVEAL_REJECTED

Each event should receive an event identifier and be processed by the Private Off-Chain Ledger Engine.

## 11. Security boundary

The engine provides commitment/reveal integrity. It does not by itself guarantee:

- honest card generation;
- honest randomness;
- secure wallet custody;
- secure endpoint devices;
- availability;
- absence of collusion;
- regulatory compliance.

Those properties belong to other protocol components or operational assumptions.

## 12. Compatibility requirement

Any implementation claiming Engine 06 compatibility must reproduce the same commitment verification result for identical canonical inputs and cryptographic parameters.
