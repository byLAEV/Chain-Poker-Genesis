# 04 — Private Off-Chain Ledger Engine

**Chain Poker Genesis by LAEV**

> Private event history, cryptographic integrity, Merkle consolidation and Bitcoin anchoring.

## Purpose

The **Private Off-Chain Ledger Engine** is the historical evidence and event-persistence layer of Chain Poker Genesis by LAEV.

It receives protocol events, normalizes them into structured records, preserves them chronologically, calculates cryptographic hashes, groups event hashes into Merkle batches, and provides the cryptographic data required for periodic anchoring to Bitcoin.

The engine separates:

- **Private operational data**
- **Cryptographic integrity evidence**
- **Public blockchain certification**

Complete event records remain off-chain.

## Architectural role

The engine operates as a cross-cutting persistence layer:

```text
Protocol Component
       ↓
Event Generation
       ↓
Event Normalization
       ↓
JSON Event Record
       ↓
UTC Timestamp
       ↓
Event Hash
       ↓
Private Ledger
       ↓
Merkle Batch
       ↓
Merkle Root
       ↓
Bitcoin Anchor
```

The ledger records evidence generated by other protocol components; it does not replace their business logic.

## Canonical event model

A Version 1.0 record may contain:

```json
{
  "event_id": "EVENT_ID",
  "timestamp": "UTC_TIMESTAMP",
  "node_id": "NODE_ID",
  "session_id": "SESSION_ID",
  "game_id": "GAME_ID",
  "hand_id": "HAND_ID",
  "engine_id": "ENGINE_ID",
  "event_type": "EVENT_TYPE",
  "event_version": "1.0",
  "payload": {},
  "previous_hash": "PREVIOUS_HASH",
  "event_hash": "EVENT_HASH",
  "merkle_batch_id": "BATCH_ID",
  "anchor_status": "PENDING",
  "bitcoin_anchor_id": null
}
```

Conditional fields such as `game_id`, `hand_id`, and `previous_hash` depend on the event and the protocol's finalized schema.

## Cryptographic integrity

Each event receives a cryptographic hash calculated from its canonical representation.

The implementation specification must define the exact:

- Hash algorithm
- Serialization rules
- Encoding
- Field ordering
- Null-value handling
- Versioning rules

The optional `previous_hash` relationship may provide an additional sequential integrity layer. Its scope must be explicitly defined before production use.

## Merkle consolidation

Event hashes are grouped into logical batches. Candidate batching policies documented by Version 1.0 include:

- Completed poker hand
- Completed game or table
- Operational cycle
- Event-count threshold
- Configurable time interval
- Explicit certification request
- Future protocol-defined policy

Each completed batch produces a Merkle Root.

## Bitcoin anchoring

Bitcoin is used as an external cryptographic certification layer.

The protocol does **not** publish complete private ledger records to Bitcoin. The anchoring layer commits the applicable Merkle Root and stores the resulting anchor reference.

```text
Private Events
      ↓
Merkle Tree
      ↓
Merkle Root
      ↓
Bitcoin Anchor
```

The exact Bitcoin transaction construction, fee policy, key custody and anchoring mechanism belong to the corresponding cryptographic/settlement specifications.

## Privacy

The operational ledger remains private and off-chain.

The architecture therefore separates:

| Layer | Function |
|---|---|
| Private Ledger | Detailed operational history |
| Event Hash | Per-record integrity commitment |
| Merkle Tree | Batch-level cryptographic consolidation |
| Merkle Root | Compact batch commitment |
| Bitcoin Anchor | External certification reference |

## Verification

A batch can be verified by:

1. Loading the relevant private records.
2. Recomputing their canonical event hashes.
3. Reconstructing the Merkle Tree using the protocol's defined ordering and construction rules.
4. Regenerating the Merkle Root.
5. Comparing it with the previously anchored commitment.

A mismatch indicates that the supplied records or reconstruction parameters do not reproduce the anchored commitment.

## Audit model

The engine supports reconstruction using:

- Event records
- Event hashes
- Previous-hash relationships, where applicable
- Timestamps
- Node and session identifiers
- Engine identifiers
- Merkle batch identifiers
- Merkle Trees
- Merkle Roots
- Bitcoin anchor references

## Non-functional requirements

The historical Version 1.0 specification identifies:

- Persistent storage
- Cryptographic integrity
- Low write latency
- Scalability
- Complete traceability
- Audit compatibility
- Blockchain-independent operational storage
- Resistance to unauthorized modification

Future versions may add indexing, compression, encrypted archival, replication, cross-node synchronization, advanced search and optimized anchoring.

## Architectural boundary

The Private Off-Chain Ledger Engine is the protocol's historical evidence layer. It does not itself define every storage technology, Bitcoin transaction format, key-management mechanism, encryption system, replication topology or deployment strategy.

Those concerns should be specified by their dedicated components.
