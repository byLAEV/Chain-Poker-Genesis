# Node Core Configuration Contract

**Status:** CANONICAL  
**Version:** 1.0.0  
**Scope:** Protocol-neutral Node Core operational configuration

## 1. Purpose

Configuration defines operational values required by Node Core. It is distinct from the Node Core manifest and from protocol-specific configuration.

Configuration MUST be schema-validated before Node Core readiness.

## 2. Canonical source

The canonical configuration schema is:

`Node Core/Configuration/Schemas/node-configuration.schema.json`

The schema is authoritative for accepted structure, types, required fields and enumerated values.

## 3. Required baseline

The reference configuration requires:

- `node_core_version`;
- `decentralized_storage`;
- `protocol_associations`;
- `cpg_protocol`.

The CPG protocol MUST remain `NOT_INSTALLED` in a fresh protocol-neutral Node Core installation.

## 4. Defaults

Defaults MUST be explicit and deterministic.

A default MUST NOT be inferred from missing fields when the field is required by the schema.

Bootstrap-generated configuration MUST be valid against the canonical schema.

## 5. Validation

Configuration validation MUST reject:

- unknown properties;
- missing required fields;
- invalid types;
- invalid enumerated values;
- duplicate protocol associations;
- activation of CPG in a fresh Node Core installation.

Validation failures MUST fail closed.

## 6. Immutability boundary

The canonical configuration schema is immutable during runtime.

Operational configuration values MAY be changed only through an explicit configuration-management operation followed by schema validation and readiness re-evaluation.

A running Node MUST NOT silently mutate its canonical configuration.

## 7. Runtime / Node Manager boundary

Runtime consumes validated configuration for readiness evaluation.

Node Manager coordinates configuration loading and operational use.

Neither Runtime nor Node Manager may redefine the canonical schema.

Neither component may treat protocol-specific configuration as Node Core configuration.

## 8. Integrity

Configuration files MUST participate in installation integrity verification.

A configuration change invalidating the recorded integrity state MUST cause verification/readiness to fail until the configuration is revalidated and the integrity state is deliberately regenerated by the authorized installation/configuration process.

## 9. Protocol isolation

`protocol_associations` identifies associations; it does not install or activate a protocol.

CPG lifecycle remains controlled by Protocol Interface.

## 10. Implementation status

Configuration is **IMPLEMENTED / PARTIAL**.

Implemented:

- canonical JSON schema;
- bootstrap configuration generation;
- Runtime readiness field validation;
- installation verification integration.

Remaining:

- centralized configuration manager;
- explicit storage mode mutation API with readiness gate;
- administrative CLI delegation to Configuration Manager;
- full negative-path test matrix.

## 11. Verification

Tests MUST verify:

1. valid configuration;
2. missing required fields;
3. unknown fields;
4. invalid enum values;
5. duplicate protocol associations;
6. CPG activation rejection for fresh Node Core;
7. deterministic defaults;
8. integrity participation;
9. runtime readiness dependency;
10. no schema authority duplication in Runtime/Node Manager.


## 12. Storage mode administration

The canonical administrative surface exposes the decentralized storage mode as:

- `LOCAL`;
- `DUAL_STORAGE`.

The CLI MUST delegate storage mode changes to `ConfigurationManager`. It MUST NOT implement its own readiness rules.

`DUAL_STORAGE` may be persisted only when the Storage/Kubo coherence verifier returns `dual_storage_ready=true`.

The administrative surface returns both the configured mode and the technical storage status. A Kubo provider degradation does not silently rewrite the user's selected mode; effective availability is reported separately by the provider/runtime lifecycle.
