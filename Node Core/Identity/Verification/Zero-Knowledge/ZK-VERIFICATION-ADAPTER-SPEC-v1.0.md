# Node Core Zero-Knowledge Verification Adapter — Specification v1.0

**Component:** Node Core / Identity / Verification / Zero-Knowledge  
**Status:** Implementation contract  
**Scope:** Generic verification boundary for zero-knowledge proofs.

## 1. Purpose

The adapter allows Node Core to verify a zero-knowledge proof presented as evidence for a protocol-controlled request without requiring Node Core to understand the application-specific meaning of the private witness.

## 2. Input contract

A verification request SHALL contain, at minimum:

- `proof_system`
- `proof_system_version`
- `circuit_or_statement_id`
- `verification_key_id`
- `public_inputs`
- `proof`
- `request_id`
- `context`

Optional fields MAY include:

- expiration;
- sequence number;
- nonce;
- protocol reference;
- manifest reference;
- evidence reference.

Private witness data MUST NOT be part of the Node Core verification request unless a selected proof system explicitly requires an internal prover operation. The verifier boundary itself is public-input oriented.

## 3. Verification sequence

```text
REQUEST
  ↓
Envelope validation
  ↓
Proof-system compatibility check
  ↓
Verification-key resolution
  ↓
Verification-key integrity check
  ↓
Public-input validation
  ↓
Context / request binding
  ↓
Replay / sequence checks
  ↓
Cryptographic proof verification
  ↓
Canonical verification result
```

## 4. Result states

The adapter SHALL return one deterministic result class:

- `VERIFIED`
- `INVALID_PROOF`
- `MALFORMED_REQUEST`
- `UNSUPPORTED_PROOF_SYSTEM`
- `UNKNOWN_VERIFICATION_KEY`
- `PUBLIC_INPUT_INVALID`
- `CONTEXT_MISMATCH`
- `REPLAY_DETECTED`
- `EXPIRED_REQUEST`
- `VERIFIER_ERROR`

An implementation MAY expose additional diagnostic data, but the canonical result class MUST remain stable.

## 5. Security requirements

The adapter MUST:

1. verify the exact proof system declared by the request;
2. bind verification to the requested statement or circuit identifier;
3. verify the intended verification key;
4. reject altered public inputs;
5. distinguish invalid proof from unsupported proof system;
6. prevent a valid proof for one request from being silently reused for another request when request binding is required;
7. avoid logging private witness material;
8. preserve deterministic verification semantics.

## 6. Protocol boundary

The adapter verifies a cryptographic statement.

It does not decide whether the statement is useful, desirable, sufficient for seating, sufficient for consensus, or sufficient for settlement.

Those decisions belong to the requesting protocol.

## 7. Reference mapping

The external reference repository uses several poker-specific circuits, including:

- `publickey1.circom`
- `encryptdeck52.circom`
- `shuffle52reencrypt.circom`
- `shuffle52final9.circom`
- `partialdecrypt1.circom`
- `finalreveal1.circom`

These are classified as **application-specific proof circuits**.

They are not Node Core circuits.

Node Core may later verify proofs generated by such circuits through this adapter if a CPG protocol component formally adopts the corresponding statement and proof-system profile.

## 8. Implementation dependency

Production implementation remains dependent on:

- final proof-system selection;
- verification-key lifecycle;
- canonical proof envelope serialization;
- approved public-input encoding;
- deterministic error contract;
- test vectors;
- security review.
